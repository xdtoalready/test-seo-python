# Программное обеспечение «SEO Entity Analyzer»
**Правообладатель:** [НАЗВАНИЕ КОМПАНИИ], ИНН [ИНН], ОГРН [ОГРН]
**Документ:** Документация, содержащая описание функциональных характеристик экземпляра программного обеспечения, предоставленного для проведения экспертной проверки

---

## 1. Общее описание

**SEO Entity Analyzer** - программное обеспечение для автоматизированного анализа семантических сущностей конкурентов в поисковой выдаче с целью оптимизации контента для GEO (Generative Engine Optimization) и AEO (Answer Engine Optimization).

**Назначение:** Извлечение структурированной информации из топовых сайтов в поисковой выдаче для формирования семантического ядра и оптимизации контента сайта.

---

## 2. Основные функциональные возможности

### 2.1. Получение результатов поиска (SERP)

**Описание:**
Модуль получает список URL из поисковых систем по заданному ключевому запросу и региону.

**Поддерживаемые поисковые системы:**
- Яндекс (yandex.ru)
- Google (google.com)

**Параметры запроса:**
- Ключевое слово (keyword)
- Регион поиска (region_id для Яндекса, location для Google)
- Глубина выдачи (depth: 1-100 результатов)
- Поисковая система (engine: yandex / google)

**Поддерживаемые провайдеры:**
- SerpAPI (реализовано)
- Yandex XML API (в разработке)
- Custom API (через конфигурацию)

**Функциональность:**
- Получение organic результатов поиска
- Фильтрация по черному списку доменов
- Поддержка пагинации (несколько страниц выдачи)
- Автоматический retry при сбоях сети

**Режимы работы:**
- DEMO: возвращает 10 предзаписанных URL
- PRODUCTION: реальный запрос к SerpAPI

**Принцип работы:** Модуль использует абстрактный интерфейс провайдера, что позволяет легко заменять источники данных без изменения кода.

**Текущая конфигурация для экспертизы:** SerpAPI (как наиболее быстрый в интеграции вариант). Переключение на российские альтернативы осуществляется изменением конфигурационного файла.

**Пример результата:**
```json
[
  "https://site1.ru/",
  "https://site2.ru/",
  "https://site3.ru/",
  ...
]
```

### 2.2. Извлечение контента с веб-страниц

**Описание:**
Модуль скачивает HTML-код страниц и извлекает основной текстовый контент, очищенный от навигации, рекламы и служебных элементов.

**Технология:** Trafilatura - специализированная библиотека для извлечения основного контента веб-страниц

**Функциональность:**
- Скачивание HTML с поддержкой редиректов
- Извлечение чистого текста (без HTML-тегов)
- Фильтрация по минимальной длине контента (>500 символов)
- Ограничение максимальной длины (до 50 000 символов)
- Обработка нескольких URL параллельно
- Обработка ошибок (404, timeout, недоступность)

**Режимы работы:**
- DEMO: возвращает 3 предзаписанных текста
- PRODUCTION: реальный парсинг страниц

**Пример результата:**
```json
{
  "url": "https://example.com/",
  "text": "Выкуп битых автомобилей в Москве. Наша компания...",
  "length": 3500,
  "truncated": false
}
```

### 2.3. ИИ-анализ текста и извлечение сущностей

**Описание:**
Модуль использует большую языковую модель (LLM) для анализа текста и извлечения семантических сущностей и связей между ними.

**Используемая модель:** DeepSeek V3.2 (через OpenRouter API)

**Поддерживаемые модели:**
- DeepSeek V3.2 через OpenRouter (реализовано)
- Любые OpenAI-совместимые API
- Возможность интеграции: GigaChat (Сбер), YandexGPT, Kandinsky

**Принцип работы:** Модуль использует стандартный протокол OpenAI API, что обеспечивает совместимость с широким спектром LLM провайдеров, включая российские.

**Функциональность:**
- Анализ текста на естественном языке (русский/английский)
- Извлечение сущностей (entities): объекты, понятия, термины
- Определение связей (relations) между сущностями
- Извлечение контекста для каждой связки
- Валидация структуры результата
- Автоматический retry при ошибках API

**Формат извлекаемых данных:**
```json
{
  "entity_1": "Выкуп битых автомобилей",
  "relation": "требует",
  "entity_2": "Паспорт транспортного средства",
  "context": "Для сделки требуется ПТС или электронный ПТС"
}
```

**Типы связей:**
- `требует` - необходимость чего-либо
- `включает` - состав, входящие элементы
- `предоставляет` - услуги, возможности
- `может_быть` - вариативность
- `осуществляется` - способ выполнения

**Режимы работы:**
- DEMO: возвращает 10 предзаписанных сущностей
- PRODUCTION: реальный анализ через DeepSeek V3.2

**Ограничения:**
- Максимум 30 связок на один текст
- Минимум 2-3 слова на сущность
- Максимум 6 слов на сущность

### 2.4. Агрегация и статистический анализ

**Описание:**
Модуль объединяет результаты анализа всех страниц, подсчитывает частоты встречаемости сущностей и формирует итоговую структуру данных.

**Функциональность:**
- Объединение сущностей со всех проанализированных страниц
- Подсчет количества источников для каждой сущности
- Категоризация по частоте:
  - **Универсальные** (universal): встречаются на 70%+ сайтов
  - **Частые** (common): встречаются на 30-70% сайтов
  - **Редкие** (rare): встречаются менее чем на 30% сайтов

**Пример агрегированных данных:**
```json
{
  "entity_1": "Выкуп битых автомобилей",
  "entity_2": "Паспорт транспортного средства",
  "relation": "требует",
  "sources_count": 8,
  "sources": [
    "https://site1.ru/",
    "https://site2.ru/",
    ...
  ],
  "contexts": [
    "Для сделки требуется ПТС",
    "Необходим паспорт ТС для оформления",
    ...
  ]
}
```

**Статистика:**
```json
{
  "total_entities": 125,
  "universal_entities": 15,
  "common_entities": 45,
  "rare_entities": 65
}
```

### 2.5. Генерация Excel отчета

**Описание:**
Модуль создает профессионально оформленный Excel файл с результатами анализа.

**Структура отчета:**

**Лист 1: "Сводка" (Summary)**
- Ключевое слово
- Регион
- Поисковая система
- Дата анализа
- Количество источников
- Общее количество сущностей
- Распределение по категориям

**Лист 2: "Все сущности" (All Entities)**
Таблица со столбцами:
- Entity 1 (Сущность 1)
- Relation (Связь)
- Entity 2 (Сущность 2)
- Sources Count (Количество источников)
- Category (Категория: Universal/Common/Rare)
- Sources (Список URL)

**Лист 3: "Универсальные" (Universal)**
- Только сущности с частотой 70%+
- Отсортированы по убыванию частоты

**Лист 4: "Частые" (Common)**
- Сущности с частотой 30-70%

**Лист 5: "Редкие" (Rare)**
- Сущности с частотой <30%

**Оформление:**
- Автоматическая ширина столбцов
- Заголовки с жирным шрифтом
- Цветовая кодировка категорий
- Фильтры на заголовках
- Защита от редактирования метаданных

**Формат файла:** `.xlsx` (Excel 2007+)

### 2.6. REST API

**Описание:**
Веб-сервис на основе FastAPI, предоставляющий HTTP API для взаимодействия с системой.

**Технология:** FastAPI + Uvicorn (ASGI сервер)

**Основные endpoints:**

#### POST /api/v1/analyze
Запуск анализа SERP и извлечение сущностей.

**Request:**
```json
{
  "task_id": "unique-task-id",
  "keyword": "выкуп битых автомобилей",
  "region_id": 213,
  "region_name": "Москва",
  "settings": {
    "depth": 10,
    "engine": "yandex"
  }
}
```

**Response:**
```json
{
  "task_id": "unique-task-id",
  "status": "queued",
  "message": "Задача поставлена в очередь"
}
```

#### GET /api/v1/status/{task_id}
Получить статус выполнения задачи.

**Response:**
```json
{
  "task_id": "unique-task-id",
  "status": "processing",
  "progress": 65,
  "message": "Анализ с помощью ИИ...",
  "results": null
}
```

Возможные статусы:
- `queued` - в очереди
- `processing` - выполняется
- `completed` - завершено
- `failed` - ошибка

#### GET /api/v1/download/{task_id}
Скачать Excel отчет.

**Response:** Файл `{task_id}.xlsx`

#### GET /api/v1/regions/search?q=<query>
Поиск регионов для автокомплита.

**Response:**
```json
[
  {"id": 213, "title": "Москва", "parent": 1},
  {"id": 1, "title": "Москва и Московская область", "parent": 3}
]
```

#### GET /health
Проверка работоспособности API.

**Response:**
```json
{
  "status": "ok",
  "version": "1.0.0",
  "timestamp": "2026-01-21T10:00:00"
}
```

**Документация API:**
- Swagger UI: http://localhost:8000/api/v1/docs
- ReDoc: http://localhost:8000/api/v1/redoc
- OpenAPI JSON: http://localhost:8000/api/v1/openapi.json

### 2.7. Поиск и автокомплит регионов

**Описание:**
Модуль для поиска географических регионов Яндекса по названию.

**База данных:** yandex_region.json (3000+ регионов)

**Функциональность:**
- Полнотекстовый поиск по названию региона
- Нечувствительность к регистру
- Поиск по частичному совпадению
- Ограничение количества результатов (limit)
- Получение региона по ID

**Пример:**
```
Запрос: "Моск"
Результат:
- 213: Москва
- 1: Москва и Московская область
- 20729: Московский (Тюменская область)
```

### 2.8. Асинхронная обработка задач

**Описание:**
Система обеспечивает неблокирующую обработку длительных задач.

**Функциональность:**
- Постановка задачи в очередь
- Выполнение в фоновом режиме
- Отслеживание прогресса (0-100%)
- Сохранение промежуточных статусов
- Обработка ошибок и возврат информации о них

**Хранилище задач:**
- Development: In-memory (словарь в RAM)
- Production: Redis (опционально)

**Жизненный цикл задачи:**
1. `queued` (0%) - задача принята
2. `processing` (20%) - получение SERP
3. `processing` (40%) - извлечение контента
4. `processing` (70%) - ИИ-анализ
5. `processing` (90%) - генерация отчета
6. `completed` (100%) - готово
7. `failed` - ошибка (с описанием)

## 3. Технические характеристики

### 3.1. Производительность

| Параметр | Значение |
|----------|----------|
| Время анализа (10 сайтов) | 30-60 секунд |
| Параллельная обработка URL | Да (асинхронно) |
| Максимальная глубина SERP | 100 результатов |
| Размер одного текста | До 50 000 символов |
| Формат отчета | Excel (.xlsx) |
| Размер отчета | 50-500 KB |

### 3.2. Ограничения

| Ограничение | Значение | Причина |
|-------------|----------|---------|
| Минимальная длина текста | 500 символов | Фильтрация нерелевантного контента |
| Максимальная длина текста | 50 000 символов | Ограничения LLM токенов |
| Таймаут HTTP запроса | 30 секунд | Защита от зависания |
| Таймаут LLM запроса | 60 секунд | Ограничение API |
| Максимум сущностей на страницу | 30 | Оптимизация качества |
| Retry попыток | 3 | Надежность при сбоях |

### 3.3. Масштабируемость

**Горизонтальное масштабирование:**
- Возможность запуска нескольких экземпляров API
- Общее хранилище задач через Redis
- Load balancer для распределения нагрузки

**Вертикальное масштабирование:**
- Настройка количества worker'ов Uvicorn
- Увеличение памяти для обработки больших объемов

## 5. Режимы работы

### 5.1. DEMO режим (для экспертной проверки)

Этот режим предназначен специально для экспертной проверки ПО. В данном режиме:
- Используются предзаписанные mock-данные
- Не требуется регистрация в внешних сервисах
- Не требуются API ключи
- Демонстрируется полный функционал ПО
- Время выполнения анализа: ~5 секунд
- Доступен без ограничений и бесплатно

**Важно:** Mock-данные являются реалистичными примерами результатов работы ПО и позволяют полноценно оценить функционал системы.

## 6. Безопасность и надежность

### 6.1. Обработка ошибок
- Все внешние запросы обернуты в try-catch
- Автоматический retry при сетевых ошибках (3 попытки)
- Логирование всех ошибок в `logs/app.log`
- Возврат понятных сообщений об ошибках пользователю

### 6.2. Валидация данных
- Pydantic модели для всех входных данных
- Автоматическая проверка типов и форматов
- Возврат 422 Unprocessable Entity при невалидных данных

### 6.3. Защита от перегрузок
- Таймауты на все внешние запросы
- Ограничение размера обрабатываемого контента
- Exponential backoff при retry

## 7. Логирование и мониторинг

### 7.1. Логирование

**Уровни логирования:**
- DEBUG: Детальная информация для отладки
- INFO: Общий ход выполнения
- WARNING: Предупреждения о нештатных ситуациях
- ERROR: Ошибки, не прерывающие работу
- CRITICAL: Критические ошибки

**Места хранения:**
- Консоль (stdout) - цветной вывод
- Файл logs/app.log - ротация каждые 500 MB, хранение 10 дней

**Формат лога:**
```
2026-01-21 10:15:30 | INFO | serp_service:get_results - 🔍 Fetching Yandex SERP: 'выкуп авто'
```

**Endpoint:** GET /health

**Проверяет:**
- Работоспособность API
- Версию ПО
- Текущее время сервера

**Использование:**
- Docker healthcheck
- Мониторинг систем (Prometheus, Zabbix)
