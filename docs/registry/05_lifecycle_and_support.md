## 2. Процесс разработки

### 2.1. Управление исходным кодом

**Система контроля версий:** Git

**Ветвление (Branching Strategy):**

```
main (master)
├── develop
│   ├── feature/new-parser
│   ├── feature/excel-improvements
│   └── feature/api-enhancements
├── release/1.0.0
├── hotfix/critical-bug
```

**Процесс разработки новой функциональности:**
1. Создание ветки от `develop`: `git checkout -b feature/feature-name`
2. Разработка и тестирование
3. Создание Pull Request (PR) в `develop`
4. Code Review (минимум 1 reviewer)
5. Merge после одобрения
6. Автоматический запуск CI/CD

**Требования к коммитам:**
- Понятное описание изменений
- Формат: `<type>: <description>`
  - `feat:` - новая функциональность
  - `fix:` - исправление ошибки
  - `docs:` - обновление документации
  - `refactor:` - рефакторинг кода
  - `test:` - добавление тестов

### 2.2. Автоматизированное тестирование

**Виды тестов:**
- Юнит-тесты (Unit Tests) - отдельные функции и методы
- Интеграционные тесты (Integration Tests) - взаимодействие компонентов
- End-to-End тесты - полный цикл работы системы

**Инструменты:**
- pytest - фреймворк для тестирования
- pytest-cov - измерение покрытия кода тестами
- pytest-asyncio - тесты асинхронного кода

**Запуск тестов:**
```bash
# Все тесты
pytest tests/

# С покрытием кода
pytest --cov=services --cov=api tests/

# Только быстрые тесты
pytest -m "not slow" tests/
```

**Требования к покрытию:**
- Минимум 70% покрытия для критических модулей
- 100% покрытие для финансовых операций (если есть)

### 2.3. Continuous Integration / Continuous Deployment (CI/CD)

**Платформа:** GitLab CI / GitHub Actions

**Pipeline этапы:**

1. **Build** (Сборка)
   - Сборка Docker образа
   - Проверка успешности компиляции зависимостей

2. **Test** (Тестирование)
   - Запуск всех тестов
   - Проверка покрытия кода
   - Статический анализ кода (flake8, black)

3. **Security Scan** (Сканирование безопасности)
   - Проверка зависимостей на уязвимости (safety, snyk)
   - Сканирование Docker образа (Trivy)

4. **Deploy** (Развертывание)
   - Публикация образа в Registry
   - Развертывание в staging окружение
   - Развертывание в production (manual approval)

**Конфигурация (.gitlab-ci.yml):**
```yaml
stages:
  - build
  - test
  - security
  - deploy

build:
  stage: build
  script:
    - docker build -t seo-entity-analyzer:$CI_COMMIT_SHA .

test:
  stage: test
  script:
    - docker run seo-entity-analyzer:$CI_COMMIT_SHA pytest tests/
```

## 3. Процесс выпуска релизов

### 3.1. Версионирование

**Схема:** Semantic Versioning (MAJOR.MINOR.PATCH)

- **MAJOR** (1.x.x) - несовместимые изменения API
- **MINOR** (x.1.x) - новая функциональность (обратно совместимая)
- **PATCH** (x.x.1) - исправление ошибок

**Примеры:**
- 1.0.0 → 1.0.1 - исправлена ошибка в парсере
- 1.0.1 → 1.1.0 - добавлена поддержка Bing
- 1.1.0 → 2.0.0 - изменен формат API запросов

### 3.2. Процесс создания релиза

**Шаг 1: Подготовка**
```bash
# Создать release ветку
git checkout develop
git checkout -b release/1.1.0

# Обновить версию
echo "1.1.0" > VERSION
git commit -am "Bump version to 1.1.0"
```

**Шаг 2: Тестирование**
- Полное регрессионное тестирование
- Тестирование в staging окружении
- Проверка обратной совместимости
- Тестирование обновления с предыдущей версии

**Шаг 3: Документация**
- Обновление CHANGELOG.md
- Обновление README.md
- Обновление API документации
- Создание Release Notes

**Шаг 4: Релиз**
```bash
# Merge в main
git checkout main
git merge release/1.1.0

# Создать тег
git tag -a v1.1.0 -m "Release version 1.1.0"

# Push
git push origin main --tags

# Merge обратно в develop
git checkout develop
git merge release/1.1.0
```

**Шаг 5: Публикация**
- Сборка финального Docker образа
- Публикация в Docker Registry с тегами:
  - `seo-entity-analyzer:1.1.0`
  - `seo-entity-analyzer:1.1`
  - `seo-entity-analyzer:1`
  - `seo-entity-analyzer:latest`
- Публикация Release Notes на GitHub/GitLab
- Уведомление пользователей

## 4. Устранение неисправностей (Bug Fixing)

### 4.1. Классификация ошибок

**По критичности:**

| Уровень | Описание | SLA |
|---------|----------|-----|
| **P0 - Critical** | ПО не запускается, полная неработоспособность | 4 часа |
| **P1 - High** | Критическая функция не работает | 1 день |
| **P2 - Medium** | Функция работает некорректно | 1 неделя |
| **P3 - Low** | Косметические проблемы, UX улучшения | 1 месяц |

### 4.2. Процесс исправления ошибок

**Шаг 1: Регистрация**
- Создание Issue в системе трекинга (GitLab Issues / Jira)
- Заполнение шаблона:
  - Описание проблемы
  - Шаги воспроизведения
  - Ожидаемое поведение
  - Фактическое поведение
  - Версия ПО
  - Окружение (ОС, Docker версия)
  - Логи

**Шаг 2: Триаж**
- Воспроизведение ошибки
- Определение критичности (P0-P3)
- Назначение исполнителя
- Оценка сложности исправления

**Шаг 3: Исправление**
```bash
# Для некритичных ошибок
git checkout develop
git checkout -b fix/issue-123-parser-error

# Исправление кода
# Написание теста, воспроизводящего ошибку
pytest tests/test_parser.py::test_issue_123

# Коммит
git commit -am "fix: parser error with special characters (#123)"

# Pull Request
# Code Review
# Merge в develop
```

**Для критичных ошибок (Hotfix):**
```bash
# От main ветки
git checkout main
git checkout -b hotfix/critical-security-issue

# Исправление
# Тестирование
git commit -am "fix(security): critical vulnerability in API auth"

# Merge в main
git checkout main
git merge hotfix/critical-security-issue

# Создать тег
git tag -a v1.0.1 -m "Hotfix: security vulnerability"

# Merge в develop
git checkout develop
git merge hotfix/critical-security-issue
```

**Шаг 4: Верификация**
- Проверка исправления в staging
- Регрессионное тестирование
- Проверка обратной совместимости

**Шаг 5: Выпуск исправления**
- Создание patch релиза (1.0.0 → 1.0.1)
- Обновление CHANGELOG
- Публикация обновления
- Уведомление пользователей

### 4.3. Система отслеживания ошибок

**Инструменты:**
- GitLab Issues / GitHub Issues - основная система
- Sentry - автоматический мониторинг ошибок в production

**Статусы Issue:**
- `open` - новая ошибка
- `in_progress` - в работе
- `resolved` - исправлено, ожидает проверки
- `closed` - подтверждено исправление
- `wontfix` - не будет исправляться

**Метки (Labels):**
- `bug` - ошибка в работе
- `enhancement` - улучшение функциональности
- `documentation` - проблемы с документацией
- `security` - проблемы безопасности
- `P0`, `P1`, `P2`, `P3` - уровни приоритета

### 7.2. База знаний (Knowledge Base)

**Структура:**
```
docs/
├── installation/     # Установка и настройка
├── api/             # Описание API
├── troubleshooting/ # Решение проблем
├── faq/             # Частые вопросы
├── examples/        # Примеры использования
└── releases/        # Release notes
```

**Типичные проблемы и решения:**

**Проблема 1: ПО не запускается**
- Проверка: `docker ps -a`
- Логи: `docker logs seo-analyzer`
- Решение: проверить .env файл, порт 8000

**Проблема 2: Ошибка API ключей**
- Проверка: баланс в личном кабинете SerpAPI/OpenRouter
- Решение: обновить ключи или переключиться в DEMO режим

**Проблема 3: Низкая производительность**
- Проверка: нагрузка `docker stats`
- Решение: увеличить RAM, оптимизировать depth

### 7.3. Мониторинг и оповещения

**Метрики для мониторинга:**
- Время отклика API (response time)
- Количество ошибок (error rate)
- Использование ресурсов (CPU, RAM)
- Количество запросов в минуту (throughput)

**Инструменты:**
- Prometheus - сбор метрик
- Grafana - визуализация
- Alertmanager - оповещения

**Критичные алерты:**
- API не отвечает > 30 секунд
- Error rate > 5%
- Память > 90%
- Диск > 90%

## 8. Резервное копирование и восстановление

### 8.1. Что подлежит резервному копированию

**Исходный код:**
- Git репозиторий (автоматически через хостинг)
- Резервные копии на локальных машинах разработчиков

**Конфигурация:**
- .env файлы (хранятся в секретах)
- docker-compose.yml

**Данные:**
- Логи (logs/) - retention 30 дней
- Отчеты (reports/) - retention 90 дней
- База задач (Redis dump) - ежедневно

**Docker образы:**
- Docker Registry с версионированием
- Все версии сохраняются

### 8.2. Процедура восстановления

**Сценарий 1: Потеря контейнера**
```bash
# Пересоздать контейнер из образа
docker-compose down
docker-compose up -d
```

**Сценарий 2: Потеря образа**
```bash
# Скачать из Registry
docker pull seo-entity-analyzer:1.0.0
# ИЛИ пересобрать из исходного кода
git clone <repo-url>
docker build -t seo-entity-analyzer:1.0.0 .
```

**Сценарий 3: Потеря данных (Redis)**
```bash
# Восстановить из backup
docker cp backup.rdb redis:/data/dump.rdb
docker restart redis
```

**Сценарий 4: Катастрофа (полная потеря сервера)**
1. Развернуть новый сервер
2. Установить Docker
3. Клонировать Git репозиторий
4. Восстановить .env из секретов
5. Запустить: `docker-compose up -d`
6. Восстановить данные из backup (если есть)

**RTO (Recovery Time Objective):** 1 час
**RPO (Recovery Point Objective):** 24 часа

## 9. Обновление зависимостей

### 9.1. Мониторинг уязвимостей

**Инструменты:**
- Dependabot (GitHub) - автоматические PR с обновлениями
- Safety - проверка Python зависимостей на уязвимости
- Snyk - сканирование Docker образов

**Проверка вручную:**
```bash
# Python зависимости
safety check -r requirements.txt

# Docker образ
docker scan seo-entity-analyzer:1.0.0
```

### 9.2. Процесс обновления

**Регулярное обновление (ежемесячно):**
1. Создать ветку `chore/update-dependencies`
2. Обновить requirements.txt
3. Запустить тесты
4. Если тесты проходят - merge
5. Если тесты падают - исправить или откатить

**Критичное обновление (CVE):**
1. Оценка критичности уязвимости
2. Срочное обновление (в течение 24 часов)
3. Hotfix релиз
4. Уведомление пользователей

## 10. Вывод из эксплуатации

### 10.1. Причины вывода из эксплуатации

- Устаревание технологий
- Появление более совершенных решений
- Изменение бизнес-требований
- Экономическая нецелесообразность поддержки

### 10.2. Процесс вывода

**Шаг 1: Уведомление (за 6 месяцев)**
- Публичное объявление о прекращении поддержки
- Указание даты End of Life (EOL)
- Предложение миграции на альтернативное решение

**Шаг 2: Прекращение новых фич (за 3 месяца)**
- Только критичные исправления
- Security патчи

**Шаг 3: End of Support (EOL)**
- Полное прекращение обновлений
- Код переводится в read-only режим
- Документация остается доступной

**Шаг 4: Архивация**
- Архивация Git репозитория
- Удаление Docker образов из Registry (кроме финальной версии)
- Сохранение документации
